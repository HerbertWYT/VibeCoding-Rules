# AGENTS.md — SDD/TDD 驱动的软件工程约束

本文件是当前软件工程的强制协作规范，适用于 Codex、Claude Code、其他编码 Agent、其子 Agent 以及由它们调用的工具。凡在本工程目录内进行分析、设计、编码、测试、构建、迁移、修复或交付，均必须遵守本文件。

本文件使用以下规范词：**MUST（必须）**表示不可省略的要求，**MUST NOT（禁止）**表示不可实施的行为，**SHOULD（应当）**表示除非有可核验理由否则必须执行的要求。模型能力、行业惯例、个人偏好和“顺手优化”均不是偏离本规范的理由。

本规范吸收 Andrej Karpathy 对 LLM Coding 常见失误的治理方向：显式暴露假设、主动管理困惑、拒绝无依据迎合、优先简单方案、执行外科手术式修改、以可验证目标驱动循环并保留人类对产品和架构的决定权。这些治理原则只约束 Agent 的工作方法，不能替代用户要求、SDD、TDD 或当前工程证据。

## 1. 工程根目录与作用域

当前工程根目录是用户明确指定的工作目录；如果用户未单独指定，则以当前 Git 仓库根目录为工程根目录；如果当前目录不是 Git 仓库，则以启动 Agent 时的当前工作目录为工程根目录。根目录中的本文件约束其全部子目录。

Agent 开始工作时 MUST 核对当前工作目录、适用的 `AGENTS.md` 或同类指令文件、仓库状态、文档入口和实际构建入口。Agent MUST NOT 因为名称相似、历史记忆、搜索结果或其他会话内容而切换到兄弟目录、父目录中的其他工程或外部工程。未经用户明确授权，MUST NOT 读取、修改或构建工程边界外的内容。

子目录可以放置更具体的 `AGENTS.md`，但子目录规则只能细化或收紧根规则，MUST NOT 取消 SDD、TDD、可追溯性、证据或作用域约束。发生冲突时，Agent MUST 明确报告冲突及文件位置，不得自行选择更宽松的规则。

Agent MUST 先检查未提交修改并保护用户已有工作。MUST NOT 覆盖无关改动，MUST NOT 使用破坏性 Git 或文件命令。除第 1.1 节明确授权的本地 Git 初始化、任务分支和任务提交外，MUST NOT 擅自提交、推送、发布、部署、安装、删除数据或修改外部环境。

### 1.1 未提供 GitHub 时的本地 Git 版本约束

用户没有在当前任务中明确指定 GitHub 仓库并授权使用时，工程默认采用“仅本地 Git”模式。Agent MUST NOT 创建或猜测 GitHub 仓库、添加或修改远程地址、登录账号、执行 fetch/pull/push、创建 PR、上传代码或发布版本。即使发现已有 `origin`，也不代表用户授权本次联网或写入；用户只提供仓库地址时，仅授权识别目标，外部写操作仍须明确授权。

Agent 开始非平凡开发前 MUST 检测准确的项目边界和 Git 根目录。若项目根目录没有 Git、也不位于其他 Git 工作树内，MUST 在产品代码修改前建立本地仓库，使用项目既有默认分支约定；没有约定时使用 `main`。初始化时应根据当前工程证据建立 `.gitignore`，排除凭据、私密数据、构建缓存、生成物和大型临时文件，再创建可审计的本地基线；无法安全判断文件性质时不得盲目全量提交。

#### Git 边界隔离

任何 Git 写操作前，Agent MUST 同时识别明确项目根目录、向上的最近 Git 根目录，以及项目内向下存在的 `.git` 目录或 `.git` 文件。只要 Git 根目录位于明确项目之外，或项目内部含有独立 Git，默认立即进入隔离模式：只允许执行 `rev-parse`、只读 `status`、只读 `diff` 等边界识别操作；禁止 `git init`、切换或创建分支、add、commit、stash、reset、clean、rebase、tag、修改配置、修改 `.gitmodules` 或触碰任何 `.git` 元数据。

隔离模式下，MUST 先由用户或 SDD 明确仓库模型。确认由上级仓库管理时，所有操作必须绑定准确的上级 Git 根目录并限定当前项目路径，且不得切换影响兄弟工程的分支、提交项目外暂存项或改变共享配置；确认当前项目应独立管理时，必须先评估嵌套仓库对上级索引和历史的影响，未经用户明确批准不得初始化；确认项目包含多个独立子仓库时，外层不得再次初始化或全量暂存，每个子仓库必须分别执行、分别提交、分别报告。任何模式都禁止删除、移动、吸收或转换其他仓库，禁止擅自改造成 submodule、subtree 或 worktree。

修改前 MUST 记录仓库根目录、当前分支、HEAD 提交和工作树状态。既有未提交内容默认属于用户，禁止擅自暂存、提交、stash、还原或混入 Agent 提交。只有准确 Git 根目录等于明确项目根目录、工作树干净且不处于隔离模式时，非平凡任务才应按项目约定创建本地任务分支；没有约定时使用 `agent/<日期>-<短任务名>`。相关测试通过后，只提交本任务文件，提交说明必须包含任务目的及关联的 SDD/TDD ID。既有修改与本任务在同一文件中无法可靠分离时，不得自动提交。

依赖、工具链、固件、协议、数据库和发布版本必须沿用工程现有版本策略并提交对应锁文件。禁止使用无边界的 `latest`、`*` 或无依据的大范围版本漂移；版本变化必须进入 SDD/TDD，说明兼容、迁移、回退和验证结果。

禁止为完成本地提交而擅自修改全局 Git 用户身份，禁止重写历史、强制更新、破坏性 reset、清理用户文件或删除分支和标签。交付汇报 MUST 给出变更前提交、任务分支、结果提交、最终工作树状态及“远程操作：无”；因用户已有修改、身份缺失或验证失败而没有提交时，必须如实说明。

## 2. 事实、要求与证据

工程事实只能来自当前工程文件、当前命令输出、当前运行结果、用户在本任务中的明确说明或经用户认可的正式文档。模型记忆、经验、常见做法和推测只能作为待核验线索，MUST NOT 被表述为本工程事实。

Agent 对信息状态 MUST 使用清晰边界：“已观察”表示从当前材料直接看到；“已修改”表示文件确已发生变更；“已验证”表示指定检查在指定环境中实际运行并得到结果；“未验证”表示没有当前证据；“假设”表示尚未获用户或正式文档确认。MUST NOT 将“已修改”写成“已验证”，也 MUST NOT 将“构建成功”写成“功能完成”。

Agent MUST NOT 编造需求、用户场景、页面、接口、字段、错误码、数据、依赖版本、目录、命令输出、测试结果、性能结论或验收状态。信息不足但不影响已有确定范围时，应继续处理确定部分并标记未知项；信息不足会改变产品行为、架构、数据兼容性、安全性或验收口径时，MUST 停止该受影响部分并向用户说明需要确认的决策。

## 3. 编码前决策与困惑治理

用户负责决定“构建什么”和批准宏观约束，Agent 负责在已批准边界内实现和验证。产品范围、系统边界、架构、子工程、公共接口、数据所有权、安全权限、兼容迁移、外部依赖及验收口径均属于宏观决定；没有用户授权或现行 SDD 依据时，Agent MUST NOT 凭模型判断替用户决定。

任何非平凡任务在编辑文件前 MUST 形成简短的“实施前判定”。凡改变可观察行为、接口、数据、架构、依赖、安全、迁移或验收，或者涉及多个文件、需要新增测试的任务，均属于非平凡任务。仅修正不改变含义的拼写、排版或明确注释时，可以省略完整判定，但仍须核对作用域。

```text
实施前判定
目标：
可验证成功标准：
用户要求与 SDD/TDD 依据：
已确认事实：
假设及其证据：
冲突、歧义与待确认项：
预计修改文件：
明确不改动范围：
最简单可行方案：
```

假设必须区分“关键假设”和“非关键实现假设”。错误后会改变产品行为、公共接口、数据、安全、兼容、架构或验收结果的假设属于关键假设，MUST 在实施前获得用户决定或正式文档证据；Agent 不得自行选一个看似合理的答案。不会改变上述结果的局部实现假设可以在显式记录依据后继续，但必须允许用户纠正。

发现文档之间、文档与代码之间、用户要求与既有实现之间存在冲突时，Agent MUST 停止受影响部分，准确指出冲突位置和当前证据，列出可选解释及实际取舍，并请求用户裁决；不受冲突影响的确定工作可以继续。禁止隐藏困惑、伪装确定性或静默选择对自己最方便的解释。

Agent 不是迎合机器。用户提出的实现方式与已批准 SDD、当前证据或明确的安全和数据约束冲突时，Agent MUST 直接说明问题、具体后果和最小合规替代方案。用户在知情后确认改变方向时，该决定成为变更来源，Agent 应先更新 SDD/TDD 再实施；禁止仅因个人偏好或抽象“最佳实践”阻碍用户的明确决定。

## 4. SDD、TDD 与可追溯性是唯一交付基线

本规范中的 SDD 指 Software Design Description，即软件设计说明及其受控的需求、架构、接口、数据和验收设计；TDD 同时指 Test Design Description 和测试驱动开发约束，即测试设计必须成文，能够自动化的行为应先有失败测试，再实现最小修复并完成回归。如果工程已有更具体的 SDD/TDD 定义，沿用现有定义，但不得弱化“规格先于实现、测试证明实现、全链路可追溯”。

每项实现必须形成闭环：

`用户明确要求或已批准需求 → SDD 条款 ID → TDD 用例 ID → 实现位置 → 当前测试证据`

闭环缺少任何一环时，该项 MUST 标记为“未完成”或“未验证”，MUST NOT 宣称已经符合 SDD/TDD。

Agent 开始修改前 MUST 查找现有文档索引、SDD、TDD、接口契约、架构决策记录和验收基线，确认唯一权威文件，禁止另建同名或同义文档造成双重真相。如果工程没有约定，默认使用 `docs/SDD.md`、`docs/TDD.md` 和 `docs/TRACEABILITY.md`。

如果 SDD 或 TDD 缺失，而用户要求开发、修改、增加功能或修复行为，Agent MUST 先根据已经确认的事实创建最小可执行基线，再修改产品代码。未知内容必须标记为 `TBD/待确认`，不得由模型补写成确定需求。会实质影响实现的待确认项没有获得用户决定前，相关代码不得实施。

SDD 至少 MUST 说明范围与非范围、用户场景、带稳定 ID 的功能与非功能要求、系统边界、架构和模块职责、接口与数据模型、状态与错误处理、安全隐私与权限、兼容和迁移要求、约束、验收条件以及待确认项。已使用的 ID MUST NOT 被重排或复用；废弃项应保留记录并标明替代关系。

TDD 至少 MUST 说明测试策略、测试环境、测试数据、带稳定 ID 的用例、关联的 SDD ID、前置条件、操作或输入、可判定的预期结果、自动或人工类型、回归范围以及证据要求。正常、边界、异常、权限、数据一致性、并发、迁移和恢复场景应按风险覆盖，不能只验证成功路径。

可追溯矩阵至少 MUST 包含 `SDD ID`、`TDD ID`、实现文件或符号、验证环境、证据状态和未解决事项。禁止用“已处理”“符合要求”之类无法定位的文字代替条款 ID、用例 ID 和实现位置。

## 5. 所有变更必须先做 SDD/TDD 影响分析

用户提出新增功能、修改功能、改变交互、改变接口、改变数据、改变配置、改变依赖、改变架构或改变验收口径时，Agent MUST 先修改 SDD 的对应规范内容与变更记录，再更新 TDD 和可追溯矩阵，然后才可实施代码。禁止先按模型理解写完代码，再倒改 SDD 为代码辩护。

实施前必须把“完成”改写成可判定的成功标准，并关联 SDD/TDD ID。诸如“优化一下”“做得更稳定”“体验更好”之类无法验真的表述不能直接进入编码；Agent 必须从用户已确认的目标或 SDD 中得到可观察、可测试的判定条件，无法得到时按第 3 节处理。

| 任务类型 | SDD 强制动作 | TDD 强制动作 | 实施门禁 |
| --- | --- | --- | --- |
| 新功能或行为变化 | 新增或修改正式条款、设计、边界和验收条件，并记录原因 | 新增或修改关联用例，覆盖正常、边界和失败行为 | SDD/TDD 有稳定 ID 且预期结果可判定后才可编码 |
| Bug 修复 | 定位被违反的 SDD 条款；若 SDD 缺失或错误，先修订；若条款已正确，保留规范原意并更新符合性或变更记录 | 先增加能复现缺陷的回归用例，再修复并回归 | 不得修改正确规格来合理化错误行为 |
| 重构 | 记录行为、接口、数据和架构影响；架构或职责改变时必须修订正文 | 保持既有用例通过，并补足暴露出的覆盖缺口 | 无外部行为变化也必须在报告中给出不影响 SDD 的证据 |
| 依赖、构建、配置或部署变化 | 更新技术约束、兼容性、安全性、迁移和回退设计 | 更新构建、安装、升级、回退和环境验证用例 | 仅本机成功不能替代目标环境验证 |
| 纯文档修正 | 保持条款含义一致，记录修正范围 | 核对引用、ID 和预期结果一致性 | 不得借文档修正暗中改变产品行为 |

任何代码变更都 MUST 在 SDD 和 TDD 中留下可追溯记录。规范行为确实没有变化时，不得制造虚假的规范变化，但仍 MUST 更新相应变更记录或追溯状态，并在交付汇报中写明“不影响规范正文”的依据。

## 6. 测试驱动实施

对可自动化的新功能和 Bug，Agent MUST 先新增或调整测试并确认该测试会因缺失功能或现有缺陷而失败，再实施满足 SDD 的最小代码，随后运行目标测试和受影响回归。无法自动化的真机、硬件、外部服务或人工验收场景，MUST 在实现前写出可重复的 TDD 用例、环境、操作和判定标准，并把未实际执行的结果标为“未验证”。

执行必须采用目标驱动循环：先定义成功标准和失败证据，再实现最简单且容易证明正确的基线，使目标测试通过；只有基线正确性已有证据后才可优化，并且优化前后的测试判定不得被削弱。每轮应能说明“观察到的失败—根因判断—本轮最小修改—实际结果”，禁止漫无目的地连续改代码。

同一失败在没有新证据的情况下连续出现两次，或者修复需要引入新的关键假设时，Agent MUST 停止重复尝试，重新检查假设、规格、环境和根因，并公开当前困惑。不得利用 Agent 不知疲倦的特性在错误方向上持续扩大改动。

Agent MUST NOT 为获得绿色结果而删除测试、跳过测试、降低断言、扩大容差、改写正确预期、隐藏失败或只测试 Mock。测试预期发生变化必须能追溯到用户批准的要求与 SDD 变更；否则测试本身不得改变。

编译、打包、静态检查、单元测试、集成测试、端到端测试、性能测试、安装启动和真实环境验收是不同证据。Agent MUST 分别报告实际完成的层级。模拟器不能证明真机行为，Mock 不能证明真实服务集成，接口健康检查不能证明业务流程，生成构建产物不能证明功能验收。

## 7. 子工程创建规则

默认 MUST NOT 创建子工程。用户或 SDD 明确要求独立客户端、服务、工具或库时可以创建；没有明确要求时，只有同时满足下表至少两个技术条件，并且现有模块结构不能合理承载时，才允许提出或实施子工程。

| 技术条件 | 判定标准 |
| --- | --- |
| 独立生命周期 | 能独立构建、测试、版本化、打包、发布或部署 |
| 独立运行边界 | 使用独立进程、运行时、平台、设备或部署环境 |
| 独立技术边界 | 使用明显不同且必要的工具链、语言生态或安全权限边界 |
| 独立复用责任 | 具有稳定公共接口，被多个组件复用，并需要独立维护和兼容策略 |

单个页面、普通功能、临时实验、一次性脚本、测试夹具、目录整理、规避重构、并行开发方便或 Agent 自己觉得“更清晰”，均不是建立子工程的充分理由。

建立子工程前 MUST 先在 SDD 中写明建立原因、职责边界、目录、依赖方向、公共接口、数据所有权、共享契约、构建测试命令、发布方式、兼容与迁移策略；同时 MUST 在 TDD 中加入子工程单测、契约测试、跨工程集成测试、失败隔离和发布验收，并更新可追溯矩阵。上述信息无法写清时，不得创建。

子工程 MUST 继承根规范。只有存在不同工具链或更严格约束时才应增加子目录规则。MUST NOT 擅自创建嵌套 Git 仓库，MUST NOT 在多个子工程复制并分别维护同一领域模型或接口真相；共享行为应由明确的契约文件约束。

## 8. 实现边界、简单优先与外科手术式修改

Agent 只能实施用户明确要求且已进入 SDD 的范围。发现相关问题可以报告，但未经用户授权和 SDD/TDD 更新，MUST NOT 顺手增加功能、重做架构、替换技术栈、改变 UI、修改公共接口、迁移数据、升级大版本依赖或清理无关代码。

“更先进”“最佳实践”“业内通常如此”“模型认为需要”“现有代码看起来可以优化”均不能单独作为产品决策来源。采用技术方案的理由 MUST 指向具体 SDD 约束、已批准的架构决定或用户明确授权；若只是工程实现选择，还必须证明它没有改变产品范围和可观察行为。

Agent MUST 采用满足当前 SDD 的最小充分变更，先选择最短、最直接、最容易验证的正确方案。新增抽象层、框架、配置系统、插件机制、通用基类、可选参数或“为未来准备”的扩展点，必须由 SDD 明确要求，或者至少存在两个当前且已确认的真实使用方；假想复用不能成为复杂化理由。

修改既有工程时，Agent MUST 在实施前列出预计修改文件，并保持周边编码风格。每个变更文件和每组实质变更行都必须能追溯到用户要求、SDD/TDD 或使其构建和验证所必需的直接原因。禁止顺便重命名、统一格式、补类型、改引号、重写注释、增加日志或错误处理，除非它们本身属于已批准范围。

Agent MUST 清除本任务自己产生且已经失效的分支、临时代码、重复实现、无用依赖和调试残留，避免把尝试过程变成永久技术债；对任务开始前已经存在、但疑似无用或无法理解的代码，只能报告，未经影响分析、SDD/TDD 依据和回归证据不得删除或改写。

实际修改范围超出“实施前判定”中的文件列表，或出现与任务无关的 diff 时，Agent MUST 停止扩张、说明原因并重新确认范围。完成前必须检查完整 diff，而不是只相信模型自己的摘要；Agent 自审不能替代项目要求的人类评审、代码评审或技术门禁。

占位实现、伪造数据、只写接口不接业务、只做页面外观、仅让测试假通过或把未完成路径隐藏起来，均不得作为完成结果。

## 9. 完成判定

只有同时满足以下条件才可使用“完成”：实施前判定已经形成且关键假设均已解决；用户要求已全部映射到 SDD；SDD 已反映当前设计和范围；TDD 已覆盖变更；实现位置已进入追溯矩阵；相关测试在声明的环境中实际通过；完整 diff 已检查且没有无关副作用；本地 Git 基线、任务变更和最终状态可追溯，且上级、下级和兄弟仓库均未被越界修改；必要的集成、迁移、真机、硬件或外部服务验证已有当前证据；未授权扩展为零；所有失败、限制和未验证项均已如实披露。

任一必要条件缺失时，状态只能是“部分完成”“受阻”或“未验证”。Agent MUST 给出缺失的 SDD/TDD ID、影响范围和证据空缺，不得用代码量、文件数量、构建成功、少量绿色测试或主观判断代替完成条件。

## 11. 禁止性红线

禁止脱离当前工程和当前证据工作；禁止隐式代替用户作出关键假设；禁止隐藏困惑或静默选择歧义解释；禁止为迎合用户而掩盖明确冲突和风险；禁止用模型推断补齐产品需求；禁止未更新 SDD/TDD 就改变行为；禁止先实现再篡改规格为实现背书；禁止无依据建立子工程；禁止为假想未来过度设计；禁止扩大用户范围；禁止修改无关文件、格式、命名、注释或既有代码；禁止留下本任务制造的失效代码和调试残留；禁止在没有新证据时机械重复失败尝试；禁止把用户既有改动混入 Agent 提交；禁止在未授权时使用 GitHub 或其他远程仓库；禁止因当前项目而初始化、切换、提交、清理、重写或改造上级、下级、兄弟 Git；禁止删除、移动或修改不属于当前项目的 `.git`、`.gitmodules` 和共享 Git 配置；禁止创建无依据的嵌套 Git、重写历史或使用无边界依赖版本；禁止隐藏失败或未验证状态；禁止把构建、Mock、模拟器或局部测试冒充完整验收；禁止改弱测试迎合代码；禁止用无关重构掩盖功能变更；禁止在交付汇报中遗漏 SDD 条款、TDD 用例、Bug 根因、假设与困惑、本地 Git 证据、验证环境或规格外实现声明。

违反任一红线时，相关工作不得标记为完成。Agent 应停止受影响部分，保留现场证据，明确报告冲突、缺口和已经产生的变更，不得继续扩大偏差。
